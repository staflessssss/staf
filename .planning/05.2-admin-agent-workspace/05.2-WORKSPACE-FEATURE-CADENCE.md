# Workspace Feature Cadence

**Purpose:** make every admin agent workspace tab a complete, shippable feature slice before moving to the next tab.

This document is the operating protocol for Phase 5.2 work. The rule is:

> One chat = one workspace feature finished end to end.

Each chat starts with a clean feature target and ends only when the feature has UI, persistence/runtime wiring, tests, independent review, fixes from that review, a git commit, and production release or an explicit documented reason why production release is deferred.

## Current Feature Order

The workspace is implemented in dependency order, not menu order:

1. `Settings`
2. `Channels`
3. `Prompting`
4. `Knowledge`
5. `Playbook`
6. `Messages`
7. `Control`
8. `Integrations`
9. `Functions`
10. `Test`
11. `Overview`
12. `Activity` later, after the agent has enough real runtime behavior to observe

`Activity` is intentionally last. Observability should summarize a working agent, not become a placeholder over unfinished configuration surfaces.

## Per-Feature Workflow

Every feature follows the same loop.

### 1. UI Discussion

Before code, agree on the operator experience:

- What job the tab does for the operator.
- Which controls are real in this slice.
- Which controls are intentionally deferred and therefore not rendered.
- What the section layout should feel like inside the common workspace shell.
- What states are required: empty, ready, dirty, invalid, blocked, loading, saving.
- What the tab should never contain, to avoid rebuilding the old all-in-one builder.

Output: concise UI decision notes in the chat.

### 2. Frontend Slice

Implement the visible workspace section:

- Replace placeholder UI with a real section component.
- Use compact operator-console patterns, not landing-page composition.
- Prefer real controls: toggles, selects, segmented controls, inputs, lists, drawers.
- Remove fake controls unless the action is implemented.
- Surface validation and warnings where the operator makes the mistake.
- Keep the tab scoped to its domain.

Done when the tab can be used visually without relying on hidden knowledge from the old builder.

### 3. Backend / Persistence / Runtime Wiring

Wire the section to the actual agent contract:

- Persist values through the existing agent save path or add the smallest necessary schema/config extension.
- Normalize loaded values from `agent.channelConfig` or the relevant model field.
- Ensure save payloads preserve unrelated workspace sections.
- Connect runtime/prompt/deploy behavior if the tab claims to affect behavior.
- Add server-side validation when invalid saved state would break runtime or operator expectations.

Done when changing the UI changes saved data and, where applicable, actual agent behavior.

### 4. Tests

Add tests at the right level:

- Section tests for exported component, required copy, visible states, and non-fake controls.
- Workspace tests for save blocking, payload shape, and draft preservation.
- Config tests for normalization/defaults.
- Runtime/prompt/deploy tests when behavior changes.

Minimum verification before review:

```bash
npx tsc --noEmit --pretty false
npm test
npm run build
```

Warnings may remain only if they are known pre-existing warnings and are explicitly reported.

### 5. Independent Sub-Agent Review

After implementation and initial tests, start a sub-agent review before committing.

Prompt format:

```text
Review the completed workspace feature slice: <feature name>.

Context:
- Intended behavior:
  <short bullet list>
- Files changed:
  <file list>
- Tests run:
  <commands and results>

Task:
1. Score the implementation from 1 to 10 against the intended behavior.
2. Identify weak spots in correctness, UX, architecture, maintainability, and test coverage.
3. Call out any fake controls, hidden regressions, over-coupling, or missed runtime wiring.
4. Recommend only changes that are worth doing before shipping this slice.

Do not edit files. Return findings and a direct ship/no-ship recommendation.
```

The main agent then:

- Accepts review findings that are materially correct.
- Applies follow-up fixes immediately.
- Re-runs targeted tests plus the full verification gate.
- Records in the final report which review comments were accepted or rejected and why.

### 6. Commit

Commit only after:

- Implementation is complete.
- Review follow-ups are handled.
- Verification passes.

Commit rules:

- One feature slice = one logical commit.
- No unrelated cleanup in the feature commit.
- Commit message starts with the feature area, for example:

```text
feat(settings): harden workspace settings controls
feat(channels): complete channel assignment workspace section
feat(prompting): wire prompting section to prompt composer
```

### 7. Production Release

After commit:

1. Push the branch.
2. Deploy to production when the slice is meant to be available immediately.
3. Verify the production URL manually or with a read-only HTTP/browser check.
4. Report the production deployment URL and any remaining warnings.

If production release is deferred, the final report must say exactly why and what blocks it.

## Definition Of Done For A Workspace Tab

A workspace tab is done only when all of these are true:

- The UI has no fake controls.
- Every visible control either works or is intentionally not rendered.
- Changes persist and reload correctly.
- The save path preserves unrelated sections.
- Runtime/prompt/deploy behavior is wired when the tab claims runtime impact.
- Invalid states are blocked before they can create broken saved config.
- Tests cover the tab's core contract.
- A sub-agent review has scored the implementation and weak spots were addressed.
- The work is committed.
- The work is deployed to production or explicitly deferred with a reason.

## Settings Status

`Settings` is functionally implemented in code:

- Agent name saves through the workspace save path.
- Bot Status controls `ACTIVE` / `PAUSED` as the agent pause/resume switch.
- Default chat state saves and affects inbound conversation policy.
- Timezone and weekly schedule save through `channelConfig.agentSettings`.
- Schedule windows affect runtime auto-reply eligibility.
- Invalid enabled schedule windows block save.
- The previous fake `Delete agent` control has been removed.

`Settings` closure checklist:

- sub-agent review must confirm the slice is shippable;
- accepted review findings must be fixed;
- the latest commit must be pushed and released to production.
